# Escenarios de Atributos de Calidad

> Síntesis basada en el capitulo 3.3 de "Software Architecture in Practice" Bass, Clements
> y Kazman (4ta ed.), Caps. 3–14.

Utilizamos un formato común para especificar todos los requisitos de control de calidad en forma de escenarios. El formato común es comprobable y no admisible a ambigüedades; no depende de los caprichos de la categorización. De este modo, aporta regularidad a la forma en que tratamos todos los atributos de calidad.
Los escenarios de atributos de calidad constan de seis partes:

- Estímulo: Utilizamos el término «estímulo» para describir un evento que llega al
sistema o al proyecto. El estímulo puede ser un suceso para la comunidad de rendimiento, una operación del usuario para la comunidad de usabilidad, o un ataque para la comunidad de seguridad, y así sucesivamente. Utilizamos el mismo término para describir una acción motivadora para las cualidades de desarrollo. Así, un estímulo para la modificabilidad es una solicitud de modificación; un estímulo para la testabilidad es la finalización de una unidad de desarrollo.

- Fuente del estímulo: Un estímulo debe tener una fuente: debe proceder de algún lugar. Alguna entidad (una persona, un sistema informático o cualquier otro actor) debe haber generado el estímulo. La fuente del estímulo puede influir en cómo lo trata el sistema. Una solicitud de un usuario de confianza no será sometida al mismo escrutinio que una solicitud de un usuario no fiable.

- Respuesta: La respuesta es la actividad que se produce como resultado de la llegada del estímulo. La respuesta es algo que el arquitecto se compromete a satisfacer. Consiste en las responsabilidades que el sistema (en el caso de las cualidades de tiempo de ejecución) o los desarrolladores (en el caso de las cualidades de tiempo de desarrollo) deben cumplir en respuesta al estímulo. Por ejemplo, en un escenario de rendimiento, llega un evento (el estímulo) y el sistema debe procesar ese evento y generar una respuesta. En un escenario de modificabilidad, llega una solicitud de modificación (el estímulo) y los desarrolladores deben implementar la modificación —sin efectos secundarios— y, a continuación, probarla e implementarla.

- Medida de respuesta: Cuando se produce la respuesta, debe ser medible de alguna forma para que el escenario pueda someterse a prueba; es decir, para que podamos determinar si el arquitecto la ha logrado. En el caso del rendimiento, esto podría ser una medida de latencia o de rendimiento; en el caso de la modificabilidad, podría ser el tiempo de trabajo o el tiempo real necesarios para realizar, probar e implementar la modificación.

- Ambiente: El ambiente es el conjunto de circunstancias en las que se desarrolla el escenario. A menudo, esto hace referencia a un estado de ejecución: el sistema puede encontrarse en una situación de sobrecarga, en funcionamiento normal o en algún otro estado relevante. En muchos sistemas, el funcionamiento «normal» puede referirse a uno de una serie de modos. Para este tipo de sistemas, el ambiente debe especificar en qué modo se está ejecutando el sistema. Pero el ambiente también puede referirse a estados en los que el sistema no está funcionando en absoluto: cuando se encuentra en fase de desarrollo, de pruebas, de actualización de datos o de recarga de la batería entre ejecuciones. El ambiente establece el contexto para el resto del escenario. Por ejemplo, una solicitud de modificación que llega después de que el código se haya congelado para una versión puede tratarse de forma diferente a una que llegue antes de la congelación. El quinto fallo consecutivo de un componente puede tratarse de forma diferente al primer fallo de ese componente.

- Artefacto: El estímulo llega a algún objetivo. A menudo se considera que este es simplemente el propio sistema o proyecto, pero resulta útil ser más preciso si es posible. El artefacto puede ser un conjunto de sistemas, el sistema completo, o una o varias partes del sistema. Un fallo o una solicitud de cambio pueden afectar solo a una pequeña parte del sistema. Un fallo en un almacén de datos puede tratarse de forma diferente a un fallo en el almacén de metadatos. Las modificaciones en la interfaz de usuario pueden tener tiempos de respuesta más rápidos que las modificaciones en el middleware.
